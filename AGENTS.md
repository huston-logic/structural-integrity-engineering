# Structural Integrity Engineering website: permanent rules

Website for Structural Integrity Engineering (structural engineering for homes, low-rise commercial buildings and glazing systems in Colorado). Next.js App Router, strict TypeScript, Tailwind CSS v4, **static export** deployed on **Cloudflare Workers**. Merging a pull request into `main` deploys automatically through Cloudflare Workers Builds; other branches get preview URLs. Never run `wrangler deploy` by hand. Read this file before changing the repo, and update it when a rule changes.

## Sources of truth

- **Copy:** `incoming/sie-site-assets/copy-deck.md` (git-ignored; exported from the Claude Doc "Structural Integrity Engineering: site copy deck"). It is the single source of every visible string. Preserve it verbatim.
- **Design:** `docs/STYLE-GUIDE.md` (style guide v3), including its approved first-screen spec. The logo files are in `public/brand/`; never redraw the mark. Where this file and those two disagree on copy or design, they win.
- **Pricing:** the site publishes no price yet (`prices.website` is empty in `site.config.ts`, and the copy deck has none). Any price comes from the owner's approved copy, never from code.
- **Contact form:** `src/components/hl/ContactForm.tsx` posts JSON to the contact Worker (`POST /api/contact`, `worker/contact.ts`), which verifies Turnstile, saves the contact (`contact.destination` in `site.config.ts`: a lead in Dylan's Pipeline app copy, or by default a row in his Google Sheet, through a Google Apps Script web app or a service account; `contact.sheetWriter`), emails Dylan and sends the automatic reply. The form shows success (by moving to `/contact-us/thanks`) only when the Worker says the note reached Dylan (the app, the Sheet or the notification email); there is no fake success state, and answers never go in the URL or in browser storage (the thanks page is static). The form has exactly the copy deck's six required fields (`contactFields` in `contact-fields.ts`: First name, Last name, Email, Phone, Project city and state, Project scope). Without JavaScript nothing is sent (no `action`, `method="post"`). See the README's "Contact form" section.

## Architecture

- `output: "export"` in `next.config.ts`. The Next.js site is 100% static: no API routes, no server actions, no runtime server code, no `next/image` optimization (images are `unoptimized`; ship pre-sized files). Server-side needs go to an external provider (scheduler, analytics) or, for the contact form, the Worker.
- `worker/` is the only server code. Its entry is `worker/index.ts`, which runs the contact Worker for `/api/*` and, only in production on the site's own domain with `editor.enabled` true, the site editor (`worker/editor/`: the MCP endpoint `/mcp`, the owner page `/owner`, OAuth under `/oauth/*` and `/.well-known/oauth-*`; docs/EDITING.md; the editor is off on this site). `wrangler.jsonc` runs the Worker only for those paths (`run_worker_first`). It has its own `tsconfig.json`, generated runtime types (`npx wrangler types worker/worker-configuration.d.ts`; regenerate after changing `wrangler.jsonc`) and tests on Node's built-in runner (`worker/*.test.ts`, mocked `fetch`, never real mail or data). It uses no libraries except `@cloudflare/workers-oauth-provider` (the editor's OAuth server, imported only by `worker/index.ts`): `fetch` for Turnstile, Resend, the Pipeline app and the Sheet writer, and Web Crypto for the service-account JWT. Where a contact is saved is chosen in one place, `saveSubmission` in `worker/contact.ts`, by `contact.destination` (`sheet`, the default, or `pipeline`: `worker/pipeline.ts` posts `{ name, email, message, business? }` to `<contact.pipelineUrl>/intake` with the `INTAKE_SECRET` secret in `X-Intake-Secret`; never in browser code, and a preview never posts to the real app). A third destination goes in that function, where it is marked (docs/PROCESS.md rule 15). The Sheet writer is chosen by `contact.sheetWriter` in `site.config.ts`: `apps-script` (the default; `worker/apps-script.ts` posts `{ secret, tab, row }` to the Apps Script in `docs/apps-script/contact-sheet.gs`) or `service-account` (`worker/sheets.ts`). **The Worker reads every client-specific value (names, email, Worker name, Sheet tabs, writer, signature colors) from `site.config.ts` through `worker/config.ts`; no client literal belongs in `worker/` or `content/auto-reply.ts`, and the tests build the Worker from a fixture config (`createWorker`) with obviously fake values.** It may import only modules from `src/` that import only each other (no Node, Next or library imports) and the import-free `site.config.ts` (`content/contact-fields.ts`, `content/auto-reply.ts`, `content/providers.ts`, `lib/contact-validation.ts`, `lib/optional-setting.ts`, `lib/pdf-scan.ts`, and for the editor `blocks/schema.ts`, `blocks/validate.ts`, `blocks/embeds.ts`, `collections/schema.ts`, `collections/definitions.ts`, `collections/validate.ts`, `collections/site-validate.ts`, `brand/*.ts` and `settings/*.ts` (not their tests), `blocks/definitions.ts`, the `blocks/library/<type>/definition.ts` files and `site-blocks/definitions.ts`), with explicit `.ts` extensions, so the form and the Worker share one set of rules. Never import `site.ts` there (it reads `process.env`). While `contact.siteEmail` is `null`, the Worker refuses to send (502, `config_incomplete`). The automatic reply has no booking link, so `contact.schedulerUrl` does not matter to the Worker. The notification email is plain text only; the automatic reply is the one HTML email, a fixed template (the copy deck's "After sending" line plus the signature) that contains no visitor input at all, and its logs hold fixed event names and status codes, never personal data or secrets. The editor's upload inbox lives in `worker/uploads/` (an R2 bucket `UPLOADS` and the Images binding `IMAGES`, only with `editor.uploads.enabled`), and files reach the repo only through a proposal, as `public/images/uploads/<id>.webp` or `public/files/<slug>-<id>.pdf`.
- `src/app/` routes only: pages, `layout.tsx`, `sitemap.ts`, `robots.ts`, `not-found.tsx`, `og.png/route.tsx`, `icon.svg`. Route files compose components and content; they hold no copy. Every site page lives in the `(site)` route group, whose layout adds the header, `main#main` and footer (`SiteChrome`; the 404 wraps itself in it too).
- **Pages are data.** Each page is one JSON file in `src/content/pages/` (`home.json` is `/`; a `--` in the file name is a `/` in the path, so `services--glazing-and-mullion-engineering.json` is `/services/glazing-and-mullion-engineering`): its path, SEO title and description, status (`live` or `archived`) and an ordered list of blocks (`type`, optional designed `variant`, optional `anchor`, `content`). One renderer (`src/blocks/BlockRenderer.tsx`, used by `src/app/(site)/page.tsx` and the `src/app/(site)/[...slug]/page.tsx` route) builds every page; the page list (`src/lib/routes.ts`) and the sitemap come from the same files (`src/lib/page-files.ts`, `src/lib/pages.ts`). Collection items (posts, videos, podcast episodes, testimonials, team) are one JSON file each under `src/content/collections/<kind>/`, with a status of `draft`, `live` or `archived`, and the business details and the notice are `src/content/business.json` and `notice.json`; the list blocks and the footer read them at build time (`src/lib/site-content.ts`). The example item of each kind and `src/content/pages/blog.json` are shipped `archived` (docs/SITE-DIFFERENCES.md, D12): nothing under `/blog` is built until Dylan has a live post and `blog.json` is restored. Never delete an item file to remove it. The header and footer menu stay in `src/content/nav.ts` (it has the Services submenu). Archived pages are not built and leave the sitemap; their files stay so they can be restored. Never delete a page file to remove a page. The thanks page `/contact-us/thanks`, the 404 and the block showcase `/blocks` (noindex) are code pages.
- **Blocks** are designed sections, registered in `src/blocks/definitions.ts`: each has a definition (description, fields with limits, designed variants, placement, motion, example) and a component. The template's library is `src/blocks/library/`; this site's own sections are site blocks in `src/site-blocks/`, registered the same way (nearly every page section is one). Page data carries no styling: only a block's variants. Site blocks use rhythm `none`: their components (in `src/components/hl/`) carry their own band spacing. Photos: a page names a picture by path and writes its alt text next to it; the size and the phone copies come from `src/content/photos.ts`. `docs/BLOCKS.md` and `docs/blocks.json` are generated from the registry (`npm run blocks:catalog`). The gate for a new block is `docs/PROCESS.md` rule 16. Where this site differs from the template: `docs/SITE-DIFFERENCES.md`.
- `src/content/` holds the rest of the copy and the site settings as typed TypeScript modules (`contact.ts` for the form, thanks and 404 copy, `contact-fields.ts`, `auto-reply.ts`, `shared.ts`, `photos.ts`, `video.ts`, `showcase.ts`, `site.ts`, `providers.ts`, `nav.ts`, `seo.ts` for the thanks page). Edit copy in the page files or these modules, never inline in JSX. Provider settings (`email`, `schedulerUrl`, `turnstileSiteKey`) are set in `site.config.ts` (`contact.*`); `providers.ts` re-exports them and `site.ts` re-exports those. The public phone number, public email, address, hours and social links (LinkedIn and the rest) are in `src/content/business.json`, not in `site.config.ts`; `site.config.ts` keeps `contact.siteEmail` (where notifications go), `business.timeZone` and the two wiring color sets `contact.emailColors` and `editor.pageColors`.
- `src/components/hl/` the v3 design primitives and page sections; `src/components/layout/` header, footer and nav; `src/components/ui/` copy helpers (`Text`, `Placeholder`, `JsonLd`, `BookCallButton`). Prefer a new small reusable component over repeating markup. Server Components by default; add `"use client"` only for real interactivity (currently: `HeaderNav`, `ContactForm`, `CountUp`, the video player `VideoFacade` and `EnterObserver`). Keep client JS minimal.
- `src/lib/` pure helpers (`metadata.ts`, `organization-jsonld.ts`, `site-organization.ts`, `serialize-jsonld.ts`, `placeholders.ts`, `fonts.ts`, `routes.ts`, `contact-validation.ts`).
- `scripts/` Node scripts: `check-placeholders.mjs` (launch gate), `preview.mjs` (static preview server that also applies the `/*` block of `public/_headers` and gzips text files like Cloudflare; tests in `preview.test.mjs`), `check-redirects.mjs` (checks that old-site URLs listed in a file 301 to a 200 page on a given base URL; tests in `check-redirects.test.mjs`), `change-scope-rules.mjs` (the one tier allow-list for client changes), `change-scope-code.mjs` (parser checks that tier 1 `.ts` files are plain data and new pages use only what the site has), `check-change-scope.mjs` (`npm run check:scope`: judges the files a branch changed against that allow-list; strict on `change/*` branches and on pull requests by the site editor's App), `change-report.mjs` (`npm run report:changes`: before and after screenshots of the pages a change touches), `image-metadata.mjs` (removes hidden camera and location data from jpg, png and webp without re-encoding), `strip-image-metadata.mjs` (`npm run strip:images`: cleans the images a branch adds or changes under `public/images/`) and `image-alt.mjs` (finds the alt text next to every use of an image); `content-lane.mjs` (prints the pages a content-only pull request touches, for the proposed content lane; not used by CI yet); `image-fixtures.mjs` is test support only. All scripts have tests beside them (`*.test.mjs`, `npm run test:scripts`). See `docs/CHANGE-SCOPE.md`.
- `tests/a11y/` Playwright + axe accessibility check (CI job `a11y`, run against the built site via `scripts/preview.mjs`); `playwright.config.ts`. `src/lib/routes.ts` is the single route list used by `sitemap.ts` and the accessibility test.
- `lighthouserc.cjs` Lighthouse CI config (CI job `lighthouse`; pages come from `src/lib/routes.ts`); `scripts/lighthouse-summary.mjs` writes the score table to the job summary.
- `public/_headers` is the Cloudflare Workers header config. `public/_redirects` holds old-site redirects (comments only until launch). `.github/workflows/ci.yml` runs the checks.
- Design tokens (colors, type scale, radii, shadows) are defined once: the palette and Tailwind theme in `src/app/hl.css`, the base layer (body, headings, focus ring) in `src/app/globals.css`. Brand is fixed on this site (docs/SITE-DIFFERENCES.md, D11): there is no `src/content/brand.json`, and the editor cannot change a color, a font or the logo. The palette is option G, "Dusk" (`dusk`, `dusk-deep`, `night`, `snow`, `mist`, `amber`, `amber-lit`, `rule`, `error`; values in `site.config.ts` `theme.colors`, generated into `hl.css` by `npm run sync:config`), and Tailwind's default palette is switched off, so only these exist. Use the tokens; never hard-code hex values in components (the OG image route is the one exception because it cannot use CSS). One typeface, Manrope (no others), declared only in `src/lib/fonts.ts` (generated from `theme.fonts`) through `next/font/google`, which self-hosts it at build time. No third-party font or script tags, with one exception: Cloudflare Turnstile (`https://challenges.cloudflare.com`), which `src/components/hl/useTurnstile.ts` loads only after the visitor focuses the contact form.

## Content rules (non-negotiable)

- The authoritative source is `incoming/sie-site-assets/copy-deck.md`. **Preserve approved copy verbatim.** Do not paraphrase, "improve", or add claims.
- **Pricing:** no price is published on the site yet (`prices.website` is empty in `site.config.ts`). Never hard-code a price, rate or dollar amount.
- Do not invent credentials, results, statistics, client names, or certifications. Do not name the former agency or its clients. Agency work is never presented as Structural Integrity Engineering client work. Do not claim time savings for a named client.
- Voice: a working engineer talking to a contractor: short, practical, confident, no hype. The approved copy keeps Dylan's own "we" (his site says "we" although he works alone), so do not change it to "I" or the reverse. Avoid "digital transformation", "unlock", "leverage", "synergy", "AI-powered".
- Unknowns are written as `[[double-bracket placeholders]]` inside content strings. The `Text` component renders them as highlighted, visible markers. Do not delete a placeholder to hide a gap; resolve it with the real value. `npm run check:placeholders` lists every unresolved one and fails while any remain; `npm run build:launch` runs it before building. Provider settings in `site.ts` (`email`, `schedulerUrl`) must also be non-null at launch (`schedulerUrl` may be `"none"`: pages omit the link), and `business.json` must hold no placeholder, and every flag in `decisionsConfirmed` must be `true`.
- Copy is rendered as plain React text. `Text` supports only `**bold**` and `[[placeholder]]`. **Never use `dangerouslySetInnerHTML`** except in `components/ui/JsonLd.tsx`, which serializes static objects and escapes `<`. No markdown-to-HTML or user-supplied HTML.

## Security rules

- No secrets in the repo, in `NEXT_PUBLIC_*` variables, or in client code. The site's only runtime and public variable is `NEXT_PUBLIC_SITE_URL`. The build step `scripts/finish-build.mjs` also reads the non-secret CI variables `WORKERS_CI`, `WORKERS_CI_BRANCH`, `WORKERS_CI_COMMIT_SHA` and `GITHUB_SHA`. `.env*` files are git-ignored except `.env.example`.
- `public/_headers` must keep: CSP, `X-Content-Type-Options`, `X-Frame-Options`/`frame-ancestors`, `Referrer-Policy`, `Permissions-Policy`, HSTS, COOP/CORP. The CSP needs `'unsafe-inline'` for scripts/styles only because the Next.js static export inlines its bootstrap scripts. Do not loosen it further. When adding a provider (scheduler iframe, form endpoint, analytics script) add only the exact origin it needs (`frame-src`, `connect-src`, `script-src`) in the same change and document it in the README.
- External links (`http(s)://`) must use `target="_blank" rel="noopener noreferrer"`. `Button` does this automatically; hand-written anchors must too.
- **Contact form Worker.** Secrets exist only as Worker secrets that Dylan sets personally (`wrangler secret put`, and `wrangler preview base-config secret put` for previews); `wrangler.jsonc` lists names only (generated from `contact.destination` and `contact.sheetWriter` by `scripts/config-rules.mjs`). Always `RESEND_API_KEY` and `TURNSTILE_SECRET_KEY`; then `INTAKE_SECRET` for the `pipeline` destination, or for `sheet` `SHEET_WEBHOOK_URL` and `SHEET_WEBHOOK_SECRET` (the `apps-script` writer) or `GOOGLE_SERVICE_ACCOUNT_KEY` and `GOOGLE_SHEET_ID` (the `service-account` writer). This site's `contact.rateLimitIds` (2201 and 2202) are listed in `docs/HOSTING.md`; `npm run check:config` rejects the template's 1001/1002 and a reused pair. The full table, with the commands and the Apps Script properties, is `docs/SECRETS.md` (names only, never values). Keep every layer: same-origin check, size limit, rate limit, honeypot (an honest error, never a pretend success), the shared validation, server-side Turnstile with hostname and action checks, the formula guard on every Sheet cell (plain text in the Sheet: RAW input for the service account, a `"@"` number format in the Apps Script), a shared-secret check and a fixed tab allow-list in the Apps Script, a plain-text notification, and an automatic reply whose HTML is a fixed template with no visitor input and no booking link. Sheet-writer and Pipeline logs hold fixed event names and status codes only, never the web-app or Pipeline URL, a secret or lead data. The notification email always sends and says whether the app or the Sheet saved the contact. Preview mode must never email anyone but the site's own address or write to the production tab (`contact.sheetTabs.production`). Never ask visitors to submit sensitive data (client or health records) through the form.
- **Site editor** (docs/EDITING.md; off until `editor.enabled`, and off on this site). One GitHub App per site, installed on that site's repo only, with five permissions: Contents, Pull requests and Issues read and write; Checks and Metadata read only. No Workflows, Administration, Actions or Secrets. Its private key is the production-only Worker secret `GITHUB_APP_PRIVATE_KEY`. Owner emails are `editor.ownerEmails` in `site.config.ts`; the Access JWT and the owner list are checked on every `/owner` request. The editor writes only `src/content/pages/*.json`, the item files under `src/content/collections/` and the settings files `business.json` and `notice.json` (it refuses every brand change: colors, fonts and the logo are Huston Logic's, D11), plus the files the owner uploaded (`public/images/uploads/<id>.webp` and `public/files/<slug>-<id>.pdf`, only through a proposal), never deletes a page file, allows one change in flight and a daily cap (`editor.dailyChangeLimit`), and shows text as plain text only. On this site the menu is `src/content/nav.ts`, so the editor cannot change it (docs/SITE-DIFFERENCES.md, D7).
- **Uploads** (docs/EDITING.md, "Uploads"; off on this site). Only JPEG, PNG, WebP, HEIC and PDF are accepted, judged by their first bytes, never by name or browser type. SVG is never accepted. PDFs with active content are refused, and `/files/*` is served as a download with a sandbox CSP.
- Scheduling is a **placeholder until a provider is chosen** (or `"none"` when there is no booking link): set `contact.schedulerUrl` in `site.config.ts` and add its origin to the CSP (`csp.*` in `site.config.ts`, then `npm run sync:config`).

Runtime dependencies are only Next, React and React DOM, plus `@cloudflare/workers-oauth-provider` for the Worker only (the site editor's OAuth server); justify any new one in the PR. Dev-only tooling (Tailwind, ESLint, TypeScript, Wrangler, and `@playwright/test` + `@axe-core/playwright` for the accessibility check, and `@lhci/cli` for Lighthouse) never ships in the site bundle. ## Motion rules

The motion design is `docs/STYLE-GUIDE.md` §9. The rules below are the guardrails. The static design is always the resting state: every animation must end exactly in it, and removing a rule must never change how a page looks.

- **Where it lives.** One motion layer, checked by `npm run check:design` (a raw duration in `hl.css`, or a keyframe that animates anything but opacity or transform, fails). Keyframes, the reveals (`.reveal`, `.reveal-zoom`), the menu panel (`.panel`) and the Services submenu (`.hl-sub`) are in `src/app/hl.css`; the shared timing tokens (`--ease-site`, `--duration-feedback`, `--duration-panel`, `--duration-underline`, `--duration-nudge`, `--duration-draw*`, `--duration-enter`) are in `src/app/globals.css`, and Tailwind's default transition uses them, so a plain `transition-colors` is already compliant. Add new motion by extending these, not per page.
- **One focal animation per page.** The home page's is the hero line drawing (`HeroDrawing`, `.hl-draw*` in `hl.css`; its lines are drawn by a transition from `@starting-style`, its delays are `draw-at-N` classes); About, Contact, Services and the three service pages each have one label-free drawing (`PageDrawing`, same `hl-draw` timing, then still); Privacy, Thanks and the 404 have none. Do not add a second focal animation to a page.
- **Never hide content behind motion.** Body copy, actions and links are visible in the initial HTML. Headline and hero intros are CSS keyframes with `both`/`backwards` fill, so they need no JS; the line drawings' strokes start hidden through `@starting-style` and a `stroke-dashoffset` transition draws them (same duration, easing and delays as the old keyframe; `npm run check:design` allows only opacity and transform in keyframes), and their dimensions and labels use `backwards` fill from a hidden `from` keyframe, so the resting state is the finished drawing (also in a browser without `@starting-style`). The only JS-gated changes are the decorative diagram, behind the `js` class that an inline script in `<head>` sets before first paint (without JS the final drawing shows), and the home numbers (`CountUp`): the real value is always in the HTML (visible without JS, plus a visually hidden copy for screen readers), and only a figure still below the fold is set to 0 and counted up by an `IntersectionObserver` when it comes into view; never under reduced motion.
- **Reduced motion.** `prefers-reduced-motion: reduce` sets `animation: none` and `transition: none` globally (end of `hl.css`), so the end state shows immediately, and the scroll reveals (`.reveal`, `.reveal-zoom`) are switched off. Any new animation must be safe under that rule (no state that only a running animation reveals).
- **Scrolling stays native.** The only scroll listener is the passive one in a client component, if one is added (off under reduced motion). The starter has none. No scroll hijacking, parallax or wheel/touch listeners. Reveal-on-view uses the CSS scroll timelines of the approved option G reference (`.reveal`, `.reveal-zoom`: `animation-timeline: view()`, no JavaScript, only where `@supports` and `prefers-reduced-motion: no-preference` allow, ending in the static design); anything that needs JavaScript uses `IntersectionObserver`.
- **No motion libraries.** CSS transitions and keyframes only.

```bash
npm run check:scope   # change scope: tier 1 (content) or tier 3 (needs the owner); compares HEAD with origin/main
npm run report:changes   # before and after screenshots of changed pages; needs `npm run build` first and Chromium or Google Chrome
npm run strip:images   # removes hidden camera and location data from images added or changed on this branch (--check only reports, --all does every image)
npm run test:a11y   # Playwright + axe; needs `npm run build` first and an installed Chromium; not part of `npm run check`
npm run test:lighthouse   # Lighthouse CI; needs `npm run build` first and Google Chrome; not part of `npm run check`
```

CI job `a11y` runs `test:a11y` on every PR. It is a required check: a failure blocks merging.

CI job `lighthouse` runs `test:lighthouse` on every PR. It is a required check: a failure blocks merging.

Client change requests are made on branches named `change/<short-name>`. On those branches the change scope check (`npm run check:scope`, `docs/CHANGE-SCOPE.md`) fails on any file outside tier 1 (tier 1 is page files that pass the content check, images and plain-data content modules), a content problem in a page file, a deleted page file (archive it instead), a bad image (not jpg, png or webp, over 500 KB, or still carrying hidden camera or location data: run `npm run strip:images`), an image that is not used with real alt text written next to it, or a new `[[placeholder]]`; on every other branch it only reports. The `change-scope` and `change-report` CI jobs are not required checks yet.

- `check`, `a11y`, `lighthouse` and `dependency-review` are required checks in the "Protect main" ruleset, and the "Require code scanning results" rule (CodeQL) also blocks merging on new alerts. Never rename or remove those jobs, add a `paths:` filter or job-level `if:` to them, use `[skip ci]`, or change `.github/workflows/codeql.yml`'s languages or category; change the ruleset first (see CLAUDE.md).
- Fix a failing `a11y` or `lighthouse` job at its cause. Do not loosen a threshold or add a `known-issues.ts` entry just to get green.
- `.github/workflows/**`, `.claude/hooks/**`, `.claude/agents/**`, `.claude/skills/**` and `.claude/settings*.json` are owner-edited: Claude's hooks block changes to them, so a workflow or hook change is written to the scratchpad and copied into place by the owner (see CLAUDE.md and `.claude/hooks/README.md`).

CI (`.github/workflows/ci.yml`) runs `check` (lint, typecheck, build, a check that the deploy artifacts exist: `out/index.html`, `404.html`, `sitemap.xml`, `robots.txt`, `_headers`, and an informational placeholder report), plus `a11y` and `lighthouse`, on every PR.

## Maintenance

- Upgrading Next.js: read the bundled docs in `node_modules/next/dist/docs/` first, then re-run `npm run check`, re-test the static export (`npm run preview`) on every route, and re-verify the CSP in the browser console.
- Adding a page: a new JSON file in `src/content/pages/` built from registered blocks, plus a nav/footer entry in `src/content/nav.ts` if it belongs in the menu. `npm run check:content` must pass; the sitemap, the route list and the accessibility check pick it up automatically. Check that it renders with no console errors at mobile and desktop widths. Adding a block: `docs/PROCESS.md` rule 16.
- Adding an Insights article: Insights is currently a "coming soon" page. The planned article format (short-version box, "Try this this week" callout, author box, CTA, related articles, `BlogPosting` JSON-LD with real published/reviewed dates) is described in the V1 copy doc; add routes, sitemap entries and a content type then. Never invent statistics; label hypothetical examples; anonymize client details.
- Launch checklist lives in the README. Every merge into `main` is a production deploy through Cloudflare Workers Builds (settings in the README's "Deploy to Cloudflare Workers" section); never run `wrangler deploy` by hand, and the owner merges.
